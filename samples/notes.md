# 现场记录

随手记的，别当规格看；口径以 README 为准。

- 出事那天，客服账号被人注册了一个几乎一样的用户名。截图发到群里，大家放大看了半天才
  看出来：里面有一个字符不是拉丁字母。日志里两个名字排在一起，肉眼完全分不出。
- 诡异的是后台判成两个人。一个 `a` 是拉丁的 `U+0061`，另一个 `а` 是西里尔的 `U+0430`，
  码位不同，字节比对当然不等。运营说「这俩看着一样啊」，我们只能说按字节就是不一样。
  这次要的就是把这层「看着像」讲清楚。
- 归一化踩过坑。上一版先把全角转成半角、再折叠大小写，同一个名字跑两遍结果居然不一样，
  因为兼容字符折完又冒出大写字母。现在的顺序定死了：大小写、全半角、零宽字符、组合字符，
  一轮不收敛就再来一轮。提交之前把「归一化过的结果再归一化不变」当成红线跑一遍。
- 表越滚越大，最大一份已经上万条。上一版图省事，把「看着像」的关系展开成等价类全塞
  进内存，机器上还跑着别的东西，进程直接被杀了。这次内存上限是硬的，别再展开。
- 零宽那批最阴。BOM、`U+200B`、`U+2060` 混进名字里，屏幕上什么都看不见，导出到表里也
  看不出差别。运营要能知道是第几位出的问题，所以我们要求每个字符都留一条证据。
- 有人问过：纯俄文、纯希腊的名字为什么不算可疑。整串里一个拉丁字母都没有，它和真的
  外文名没法区分，拦下来就是误伤。这条口径 README 里写了，审核时别再当成漏判。
- 只回一句「可疑」运营没法处理。要能指出来是哪两个字符看着像、命中了哪条规则，他们才
  能人工复核、才敢封号。
- 网页是给规则评审用的：左边一列出问题的名字，点开右边把可疑字符高亮出来并标出它像
  哪个字符，顶部给这批用例的统计。高亮的位置和依据必须直接来自引擎的输出，别在页面里
  另算一遍，不然对不上账。
- 供应商给的那份大表里有一段是压测用的合成条目，码位在 CJK 区，样例里不出现这些字符。
  真实语料还在整理，别把合成条目当业务规则。
